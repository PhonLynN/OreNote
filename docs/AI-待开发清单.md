## ⭐ 2026-10-04 第九轮（**versionCode 718**）—— 按 DS 对齐渲染，找到一条贯穿性的设计错误

用户连续给了七张截图做 DS App 与 OreNote 的双端对比，并给了一句关键批评：

> 「如果符号间隙问题还需要我指出具体位置，说明你的渲染器设计**对不同字符是不公平的**，
>   现在字符之间的空隙是不一样的，有些留了，有些没留，我完全没法给你一一指出」
>
> 「这些问题可能都不仅仅出现于我展示给你的情景，
>   所以不要针对于这一种特定文本模式做修复，而是试图找到底层原因」

### 贯穿性的设计错误（已修，写进代码注释）

**用「字符/形状的局部特征」做判定，而不是用「它在数学/文档结构中的角色」。**
同一个错误出现了三次：

| # | 把什么当成了什么 | 后果 | 改法 |
|---|---|---|---|
| 1 | 把**字符**当成判定依据（而非它的**原子类型**） | 白名单漏字符 → 空隙时有时无 | TeX 的 `AtomType` + 封闭的 8×8 间距表 |
| 2 | 把 `\mathbf{}` 的花括号内容当成**文本**（而非**数学**） | `\boldsymbol{\tau}` 里的 `\tau` 带反斜杠露出 | 加粗类走 `parseRequiredGroup`，`\text{}` 才原样取 |
| 3 | 把 `\,` 当成**内容字符**（而非**间距**） | 只有 `μ` 和 `δ` 之间偏大 | 新增 `MathNode.Space(em)`，间距不占原子 |

> **以后再遇到渲染问题，先问"这个东西在语法上是什么身份"，而不是先看它的字形。**

### 另一条被删除的自造规则

**「整行粗体 = 小节标题」这条规则没有规范依据，已整条删除。**

| | `**体积力**` 单独成行 |
|---|---|
| CommonMark / GFM | **粗体段落**，不是标题 |
| DS（remark-gfm） | 按规范 → 粗体段落 |
| 我们（删除前） | L2 标题，字号放大 1.35 倍 |

用户图二报的「明明是列表内容却被误解析为小标题」就是这个。
现在标题**只认 `#` 系列**，与规范一致。
随之删掉全部补丁：`boldHeadingAt`、`gluedBoldSectionAt`、`stripListMarker`、
`LABEL_MAX` / `LABEL_TAIL_CHARS` / `BOLD_HEADING_*`。

### 收流层的根因（**最重要的一条**）

用户报「渲染错乱、标题与正文粘连」，六张截图都是同一形状。真正的原因**不在渲染器**：

`StreamAccumulator` 用 `isNotBlank()` 判断正文分片，而 `"\n\n".isNotBlank()` 是 **false** ——
**SSE 里单独成片的换行被整片丢弃**，块结构信息在收流层就没了。
下游渲染器再想补回来只能靠猜，这就是之前几轮"在渲染层加启发式"全部失败的根因。

实测：换行完整 31 个块 vs 换行被吞 **16** 个块 —— 一半结构丢失。

改法：`isNotBlank` → `isNotEmpty`（三处：正文增量、推理增量、`build()`）。
`isNotBlank` 的职责只是挡 JSON `null`（`optString` 把 JSON null 变成字面量 `"null"`），
不该把合法空白一起挡掉。

## ⭐ 2026-10-04 第八轮（**versionCode 630**）—— 加号菜单

用户 2026-10-04 定的形态，本轮实现：

> 「可以合成在悬浮输入框里的加号按钮里，点击加号按钮，弹出一个菜单列表，
> 包含"导入文件 / 会话文件 / 关联项目"，前两个都好理解，
> 关联项目是可以选择 orenote 内部的日程，待办，卡片，规划等内容」

### 三层结构

```
＋ → Root    导入文件 / 会话文件 / 关联项目
     Files   本会话的附件列表（含"待整理"的 UNASSIGNED）
     Link    orenote 内部对象的多选（最近 60 条）
```

后两项**不是点击即执行** —— 都要先让用户选东西，所以各自展开一页。
只有「导入文件」直接拉起系统选择器（选完自动跳到 `Files` 页，
因为用户下一步自然是想确认"进来了没有"）。

| 文件 | 作用 |
|---|---|
| `v2/ai/PlusMenu.kt` | 菜单三页的界面（根 / 文件 / 关联） |
| `ChatViewModel.PlusMenuPage` + `LinkedItem` | 状态与数据形状 |
| `buildPromptWithLinks()` | 把关联资料拼进要发给模型的文本（**顶层纯函数，可测**） |

### 「会话文件」顺带解决了「待整理文件没有界面入口」

那些文件一直存在（AI 能通过 `list_files` 看到），但用户在 App 里**看不到** ——
现在从这一页进。空态直接给「导入文件」入口，而不是一句"没有文件"
（空列表本身就是"我该做什么"的问题）。

### 「关联项目」的两条关键决定

**1. 内容在"选中时"就取好，不等到发送**

用户在挑的时候看到的就是这份内容；发送时再查一次可能已经变了
（那条日程被改了），于是"我选的那个"和"AI 看到的"不是同一个东西。

**2. 并进用户消息的正文，而不是走多模态附件**

这是**唯一一条不需要新增协议**的做法。做成附件要引入多模态 `content` 数组，
那会破坏"换一家 API 只改配置"的兼容性承诺（各家支持不一致）。

⚠️ 因此**气泡与请求是两份内容**：

| | 内容 |
|---|---|
| 气泡（`turn.content`） | 用户打的那句话 |
| 请求（`promptOverride`） | 用户那句话 + `---` + 关联资料 |

只发气泡内容 = 关联功能完全失效；把资料塞进气泡 = 对话看起来乱七八糟。
两者必须分开，`ask()` 新增了 `promptOverride` 参数承接这件事。

关联是**一次性**的：发出去就清空（否则用户会看到"我明明取消了，AI 还在引用"）。

**新增单测**：`LinkedPromptTest`（7 项）—— 它守的三个判断
（拼没拼进去 / 顺序 / 空正文如实说明）**错了都不会报错**，只能靠测。

## ⭐ 2026-10-04 第六轮补丁（**versionCode 627**）

用户第六张截图报了两个渲染问题，并给了**两段逐字原文**。

### ⚠️ 先说清楚：图一的公式**不是**渲染的锅

用户原话确认了：「第一个是 ai 自己的问题，**没有使用 latex 代码格式**」。

| | 模型怎么写 | 结果 |
|---|---|---|
| 图一 | `ρ(∂**u**/∂t + (**u**·∇)**u**)` —— 纯 Unicode 字符 | 只能是普通文字（**没有 LaTeX 可排版**） |
| 图二 | `$$\rho\left(\frac{\partial \mathbf{u}}{\partial t}…$$` | 渲染成**真正的分式** ✓ |

同一个方程两次写法不同 —— 这是**模型输出不一致**，不是渲染器缺陷。
所以这一轮**没有**去"让 Unicode 公式变好看"（那做不到，也不该做）。

### 真正修的四件事（图一 2 个 + 图二 2 个）

| # | 现象 | 根因 |
|---|---|---|
| 25 | `**整行粗体**` 当小节标题时**不被识别** | 只认 `#` 系列，不认"整行粗体"这种等价写法 |
| 26 | `…重力**物理含义**` 粘在条目尾部 | 行级预处理里没有"粘着的粗体标记"这一条 |
| 27 | `##标题…` **吞掉整段正文**（一大段变粗体） | `sentenceCut` 取"最后一个标点"，而不是长度合适的那个 |
| 28 | `###每项背后的物理\|项 \|对应物理 \|` 表格整块平铺 | 表格分支优先于标题分支，`###…` 成了**第一格的内容** |

### 关键判据（写进注释了）

- **`sentenceCut` 重写**：句末标点（`。？`）在 `HARD_TITLE_LIMIT=40` 内就收；
  句中停顿（`，、`）只在 `MAX_TITLE=12` 内收；都不满足则**长度硬切**。
  ⚠️ 上一版这时返回 -1（整行当标题），后果是**整段 20 多行全变标题**。
- **块标记太靠后不算断点**：`##…**粗体**…` 里那个 `**` 在第 66 字，
  以它当断点等于整段变标题。所以 `cut > HARD_TITLE_LIMIT` 时忽略它。
- **表格头摘标记**：新增 `splitLeadingBlockMarker`，把表头第一格里的
  `#` / `**` 摘成独立的标题块。
- **`boldSectionHeading`**：整行 `**…**` 且中间无别的 `**`、长度 ≤24 → 当二级标题。

### ⚠️ 我又踩了同一个测试陷阱（第二次）

写"不残留 `**`"的断言时，我又去查 `Block.toString()` —— 那是**原始 Markdown**，
`**` 本来就该在。**解析层与渲染层是两件事**：

| 层 | 该不该有 `**` |
|---|---|
| `Block.text`（解析结果） | **该有** |
| `renderInline(...).text`（渲染结果） | **不该有** |

改成对 `renderInline` 断言。这个错我上次已经犯过一次并记在注释里，
**这次又犯了** —— 所以在测试里写明了"别再这么写"。

**新增单测**：`RealReplySixthShotTest`（15 项，**逐字照抄用户两段原文**）。

### 第 23 条：括号配对优先

`sentenceCut` 重写，判据顺序改成：

1. **括号配对**（最优先）—— 标题里开了 `（` 且同行闭合 → 在闭合处收住；
   括号**没闭合**也整行不切（硬切会把括号劈开，比标题长刺眼得多）
2. 顿号/逗号（取最后一处）
3. 冒号/句号
4. 长度兜底

`##常见形式（不可压缩、常密度）` → **整行当标题，一个字不切** ✓

### 第 24 条：标题改走 `InlineText`

标题本身已是 `SemiBold`，再叠粗体没视觉差别，但**标记必须被吃掉**
（露出 `**` 才是 bug）。

**同时加了一道防线**：`标题分支必须使用 InlineText` 是一条**源码级**断言
（读 `AiMarkdownText.kt`，检查 `is Block.Heading ->` 分支用的是哪个组件）。
JVM 单测没法测"用了哪个 composable"，这是唯一能守住它的办法。

⚠️ 这条断言带**自检**：同时拿一段用 `VText` 的假源码喂给同一个判定函数，
确认它返回"不合格"。不做自检的话，万一片段截取逻辑有 bug（永远截到空串），
这条测试会**假绿** —— 那比没有测试更糟。

### 修法

1. **标题分支改为"切开"**（新增 `splitHeadingAndBody` + `sentenceCut`）：
   `##标题正文粘一起` 时，标题只取开头一段，**其余塞回待处理列表**
   再走一遍完整块判定 —— 于是它里面的 `-` 条目、`##` 都能被正常识别。
2. **`splitGluedBlockMarkers` 不再跳过 `-` 开头的行**：
   列表项**自己那一行里也可能粘着别的标记**（`- xx##yy`），
   旧判据整行跳过，正是"`##` 露在圆点后面"的原因。
3. **remainder 要塞回去前再过一遍预处理**（它里面可能还有粘着的标记）。

### ⚠️ 一个必须说清楚的限制：有些行**无法完美切分**

```
##它从哪来流体里随便取一个小块，它受力包括：
```

「它从哪来」与「流体里随便取一个小块…」之间**没有任何格式信号** ——
边界信息在字符串里**根本不存在**，任何规则都只能猜。

我选了「**切在第一处标点**」而不是"切在第 N 个字"，理由是代价不同：

| 猜法 | 观感 |
|---|---|
| 切在第 N 字 | 标题短了，但**正文从词中间断开**（`小块` 孤零零） |
| 切在第一处标点 | 标题偏长（整句），但**正文一个字没断** |

**以后不要再试图"调参数修好它"** —— 修不好的，只能选代价最小的猜法。
真正干净的解法是**提示词里要求模型在小节标题后换行**（待做）。

**新增单测**：`RealReplyFourthShotTest`（11 项，**逐字照抄用户原文**）。

## 1. 工具集（Tool Calling）—— 最大的缺口

### 现状

`ChatProtocol.kt` 里 `ToolSpec`、`ToolCall`、`ChatMessage(role="tool")`、
`StreamAccumulator` 的工具调用增量累积**全都写好了**，
`ChatRequest.tools` / `allowTools` 也已经能正确组装请求。

但是：**`tools` 从来没有被赋过值。** 全项目没有任何一处定义过一个工具。
`AiSettings.enableTools` 这个开关也因此**暂时不产生任何效果**（注释里写明了）。

界面上「助手模式」和「聊天模式」目前**行为完全一样** —— 这是刻意的诚实做法，
不是漏了。等工具有了，助手模式才有区别。

（实现上：`ChatViewModel.mode` 只被存下来和显示出来，
`sendMessage()` **从头到尾没读过它**。所以切换模式今天不改变任何行为。）

### 设计稿已经画好了

- `AI · 对话 · 工具调用`（`jTU7u`）—— 工具卡片长什么样：
  标题「创建日程」+ 状态「已完成」+「调用参数」+「返回结果」
- `AI · 对话 · 提问工具`（`J8NaSL`）—— `ask_user` 的交互：
  单选/多选选项、「其他（请自行输入）」、提交、`1 / 2` 分页

### 工具清单（草案，未实现）

`verification/plan030/tool_design.py` 里有完整推导。收敛后的清单：

**读（10 个）**

| 工具 | 用途 | 复用 |
|---|---|---|
| `get_schedule` | 某时间范围内的日程（重复规则展开后的实例） | `BuildAgendaUseCase` + `ExpandRecurrenceUseCase` |

| `get_terms` | 学期/周期 | — |
| `get_daily_reviews` | 每日复盘 | — |

**写（7 个，不确认）**：`create_item`（含 `remind`）、`update_item`、`create_note`、
`log_habit`、`log_quantity`、`save_daily_review`、`toggle_checklist`

**删（1 个，必须确认）**：`delete_items` —— 见第 4 节

**交互（1 个）**：`ask_user`

### 设计原则（踩过坑才定下来的）

1. **工具对应「用户意图」，不对应「数据库表」**
   坏：`query_items` / `query_board_cards` / `query_courses`（暴露表结构）
   好：`find_free_slots` / `search_notes`
   理由：表结构是实现细节。AI 看到表名会开始做「表连接」式推理，
   而它不知道 `treePath`、`orderIndex` 这些内部概念，必然用错。

2. **能复用 UseCase 的就复用**，不要绕过它们直接写库 ——
   重复规则、物化路径、排序这些复杂逻辑已经在 UseCase 里了。

3. **工具数量要少。** 每个工具都占 prompt，模型还要在其中选。
   20 个工具会让选择质量下降。

### 明确不做

- **`query_database`（通用 SQL）** —— AI 不懂 `treePath` / `orderIndex` /
  复合主键，必然用错；而且无法预知它会做什么，无法测试。
  这是最危险的「万能工具」。
- **`get_all_items`（全量读取）** —— 正是「不要用数据库填满上下文」要避免的，
  而且贵约 75 倍。
- **每个表配一个查询工具** —— 暴露实现细节。

### 未决

- **`preview_changes`**（批量写之前先给 diff）—— 我倾向于**不做**，
  但没得到确认。
- **工具批量调用** —— 我倾向于先把主干跑通，同样没确认。

## 2. RAG 检索层 —— `search_notes` 的前置依赖

### 现状

**一行代码都没有。** 没有 embedding 客户端，没有向量索引。

设置页上「向量模型」那一行是**故意没有 `onClick`** 的（不是漏了），
副标题固定显示「未配置」—— 接口还没实现，做成可点的会更糟。
`AI · 向量模型配置`（`iI6i8`）这一页的稿子存在，但没建。

### 已定的决策

- **向量存文件，不建表。** 理由是向量可以从原文重新算出来，
  属于「派生数据」，不该进数据库、也不该参与云同步。
  这也绕开了 v11 schema 冻结的限制。
- **嵌入模型：Qwen3-VL-Embedding**（阿里云百炼），文本 0.7 元/M token、
  图片 1.8 元/M token。

### 成本（已实测推算）

- 首次全量索引 ≈ **0.35 元**
- 之后每月增量 ≈ **0.2 元**

### 一个必须先说清的结论

**RAG 省的其实不是嵌入成本，是对话成本。**

- 一轮对话（走 RAG）≈ 0.0034–0.0067 元
- 一轮对话（全量塞上下文）≈ 0.064 元

差约 **10–19 倍**，而且全量塞迟早会撑爆窗口。
所以 RAG 的价值在**对话侧**，嵌入那点钱可以忽略。

### 待做

- [ ] embedding 客户端（multimodal：文本 + 图片）
- [ ] 向量索引的存储格式与读写
- [ ] 分块策略（一条笔记切几块、按什么切）
- [ ] 混合检索（语义 + 关键词，纯语义对专有名词不友好）
- [ ] 增量索引（内容改了要重算）
- [ ] `AI · 向量模型配置` 页面（稿子 `iI6i8` 已画好）
- [ ] 图片索引 —— 用户明确说过**不在乎隐私**，

## 5. 四指下滑唤出手势 —— 被删了，没恢复

### 现状

`AiGestureHost.kt` 现在是**空壳**：只有 `Box { content() }`。
真正的实现（`awaitEachGesture` + 4 指针判定）在调试期间被我删掉了，
**至今没有恢复**。文件里还留着两个没人用的常量
（`REQUIRED_POINTERS = 4`、`THRESHOLD_DP = 60f`）。

目前**只能靠点五个主页面的 AI 按钮进入**，手势是废的。

### 已定的口径

- 四指**下滑**，≥ 4 个手指同时按下，整体下移超过 60dp
- **不论在哪个界面都能唤起**（二级页、编辑弹窗、白板卡片拖到一半）
  → 所以检测必须放在**整棵界面树之上**，不是各页面自己实现
- **全屏浮层，不是导航跳转** —— 退出后要回到原来的位置
- **不加额外保护**：不判速度、不要求二次确认、不显示提示。
  用户原话：「四指的误触概率低得可怕」
- 不判速度的理由：慢速稳定下拽和快速甩下都该生效

### 待做

- [ ] 把 4 指针检测装回 `AiGestureHost`
- [ ] 确认它与列表滚动、白板长按拖拽不冲突
      （Compose 在 pointer 数量上天然区分：列表滚动是单指驱动的）

## 6. 对话存储要换实现（有明确阈值）

### 现状

`ConversationStore` 把**全部**会话和轮次存在 `app_meta` 的**一个键**里
（`ai.conversations`），每次写入是**整块重写**。

### 代码里写明的边界

> 当会话数超过约 **200 个**、或总轮数超过约 **5000** 时，应当改成真正的表。

到那时整体重写一次的代价就明显了（数 MB 的 JSON 反复序列化）。
改表意味着动 schema（**v12**），而那是一次独立的重构 —— 不要顺手做。

### 待做

- [ ] 达到阈值后：`conversations` + `turns` 两张表，迁移 `app_meta` 里的旧数据
- [ ] 迁移要参与云同步

### ⚠️ 顺带发现的一个更大的问题：AI 数据现在完全不进备份

AI 的设置和会话都存在 `app_meta`，而 **`app_meta` 不进备份**
（历史决定：它混了设置与未保存草稿，见 `SyncSettings` 的注释）。

后果：**换机 / 恢复备份后，你的 AI 配置和全部对话会一起消失。**
这跟「上表才能同步」是同一个根因的两面 —— 迁移到真表时，
「AI 数据要进备份」这个需求必须一起解决，不能只搬数据不改备份范围。

## 7. 联网搜索 —— 明确不做
