# OreNote 云同步 · 设计

> 日期：2026-10-02 · 状态：**设计待确认**（确认后开工）
> 后端：Cloudflare R2（S3 兼容）· **客户端加密 · 不做登录**

---

## 1. 一句话

**每个顶层实体一个对象，整体覆盖 + HLC 定序 + 墓碑传播删除**，
数据在**客户端**加解密，R2 只是密文仓库，服务端看不到任何明文。

不做登录 = 没有账号体系；**凭据本身就是身份**（Access Key 存在本机加密存储里）。

## 2. 数据放在 R2 上的形状

```
bucket/
  <keyPrefix>/                     ← 一个「同步空间」，由用户在设置里填（见 §6）
    meta.json                      ← 空间元信息：schema 版本、设备列表、最后写入时间
    entities/
      item/<id>.bin                ← 一个顶层实体一个对象（密文）
      board_card/<id>.bin
      course/<id>.bin
      tag/<id>.bin
      ...
    blobs/
      ab/<sha256 前 2 位>/<sha256>.bin   ← 附件二进制，**内容寻址**（密文）
    tombstones/
      <table>/<id>.bin             ← 删除墓碑（密文），保留 N 天后可清理
```

### 附件走 `blobs/`，与实体分开（用户 2026-10-02：所有附件都要同步）

**内容寻址**（对象名 = 文件内容的 sha256）是这里的关键：

- 同一张图在两台设备上**天然同名** ⇒ 重复上传自动跳过（先 `HeadObject` 探一下就知道在不在）；
- 附件与实体的关系用**引用**表达，而不是"传文件"：
  `AttachmentEntity` 增加 `contentHash`（走 `entity_ext` 抽屉，见 §3），
  同步的是"某条附件记录指向某个 hash"，二进制本身按需拉取；
- 删除附件**不删 blob**：可能还有别的记录引用同一个 hash。
  blob 的回收靠"引用计数 + 延迟清理"（与现有孤儿附件清理合并，见 §3.1）。

**上传路径按大小分两档**（R2 的 S3 API 已实现分片，已查证）：

| 大小 | 方式 |
| --- | --- |
| < 8MB | `PutObject` 一次 |
| ≥ 8MB | `CreateMultipartUpload` → `UploadPart`(≥8MB/片) → `CompleteMultipartUpload` |

分片上传要能**断点续传**：把 `uploadId` 与已完成分片号存 `app_meta`，
中断后重新同步时不从零开始（大 PDF 走移动网络时很关键）。

**下载策略**（否则云盘会变成流量黑洞）：

- 默认**按需下载**：附件行同步过去，但二进制等用户真正打开时才拉；
- 列表里显示一个"未下载"角标（复用现有附件行的样式）；
- 设置页提供「仅 Wi-Fi 下载附件」开关（默认开）；
- 拉下来的文件存本地缓存目录，按 LRU 淘汰（保留期设置项留到 S6）。

**为什么一个实体一个对象**（而不是一个大 JSON）：
- 冲突粒度 = 实体粒度。两台设备改**不同**目标时不会互相覆盖；
- 增量同步只传变化的实体（省流量、省 R2 的 Class A 操作次数）；
- `PutObject` 支持 `If-None-Match` / `If-Match` 条件写 —— **这就是并发保护**，
  不需要额外的锁服务。

**每个对象的内容**（密文解开后）：

```json
{
  "table": "item",
  "id": "uuid",
  "rev": 7,               // 每次修改 +1
  "hlc": "0000019a-0003-a1b2",  // 混合逻辑时钟，用于定序
  "deviceId": "uuid",     // 哪个设备最后写的
  "deletedAt": null,      // 非空 = 墓碑
  "updatedAt": 17863...,
  "payload": { ... }      // 该实体的完整字段（含 entity_ext 抽屉）
}
```

## 3. 同步元数据放哪（受 v11 冻结约束）

`items` 等老表**已被 `SchemaFreezeTest` 冻结在 v11，不能加列**。
所以同步元数据走两条路：

| 数据 | 放在哪 | 理由 |
| --- | --- | --- |
| **每个实体的 rev / hlc / deviceId / deletedAt** | `entity_ext` 抽屉，键名 `sync.rev` / `sync.hlc` / `sync.device` / `sync.deleted` / `sync.deletedAt` | 老表永不改，符合项目第一条硬性标准 |
| **附件的 contentHash**（内容寻址的键） | `entity_ext` 抽屉，键名 `sync.blobHash` | 同上；老表 `attachments` 不加列 |
| **设备身份、R2 凭据、开关、最后同步时间、分片上传状态** | `app_meta`（现有 KV 表，JSON 值） | 设置类数据，本来就在这 |

⚠️ `attachments.storedPath` **仍然保留**（本地缓存的实际位置），
`sync.blobHash` 是**它在云端的身份**。两者含义不同，不要混用：
本地路径换机就失效，hash 永久有效 —— 这正是"路径不能跨端"那个问题的解法。

### 3.1 孤儿附件清理必须改（软删带来的连带影响）

`OrePlanApplication.sweepOrphanAttachments()` 现在的逻辑是：
**「磁盘上有文件、但库里没有索引行」⇒ 删文件**。

改成软删后会出现一个**数据丢失事故**：

> 用户删了一条带附件的待办 ⇒ 附件索引行被软删（行还在，被过滤掉）⇒
> 但如果清理逻辑用"过滤后的有效集合"去比，那个文件就变成"孤儿"被删掉。
> 而墓碑还在、同步会把它传到另一台设备 —— **另一台设备上点开附件，文件已经没了。**

所以清理逻辑必须**按"物理存在"判断，而不是"逻辑可见"**：
orphan 判定要用**未过滤的**附件行集合。同理，附件文件也不能跟着业务行一起删 ——
在墓碑被清理（90 天）之前，文件都得留着。

这条已列为 S1 的必改项，并且要有一条测试守着：
**「软删带附件的实体后，附件文件仍然存在」**。

### 墓碑的「查询过滤」问题（这是本设计最容易出错的地方）

改成软删后，**所有查询都必须排除 `deletedAt != null` 的行**，否则删掉的东西会回到界面上。
`entity_ext` 是**独立的表**，无法参与 `items` 的 SQL 过滤 ——
所以不能"查完再过滤"，那样：

- 列表数量对不上（分页会少）；
- 树形结构会出现"父在子不在"；
- `treePath` 前缀查询会带上已删子树。

**方案：内存里维护一张 `deletedIds` 快照**（`@Singleton`，启动时读一次 `entity_ext`
里 `sync.deleted` 非空的键），在仓储层出口统一过滤。理由：

- 墓碑数量天然很少（用户删过的东西），全量放内存没有压力；
- 只在**仓储出口**一处过滤，而不是散落到几十个查询点；
- 新增查询忘记过滤时，还有一层兜底（见 §7 的测试）。

⚠️ 这层的正确性靠测试保证：**「删除后，各模块列表/树/搜索/统计里都不再出现」**
要有一条覆盖全模块的测试，否则一定漏。

## 4. 冲突合并（按数据类型分治）

HLC 只解决"谁先谁后"，解决不了"两边都改了"。逐类处理：

| 数据类型 | 策略 | 说明 |
| --- | --- | --- |
| **标量字段**（标题、日期、颜色、进度） | **逐字段 LWW**（按 HLC 比大小） | 两边改不同字段 ⇒ 都保留；改同一字段 ⇒ HLC 大的赢 |
| **删除 vs 修改** | **删除优先**（墓碑赢） | 否则"在 A 删了、在 B 改了"会让它复活，违反直觉 |
| **集合型**（打卡记录、标签关联、清单项） | **按 id 并集**（add-wins） | 两边各加一条 ⇒ 两条都在；不做减法，删除靠墓碑 |
| **数值累加**（专注时长等） | 已是独立行（`focus_sessions`），按行并集 | 不需要计数器 CRDT |
| **排序**（`orderIndex` Double） | LWW + **重编号兜底** | 并发重排后可能出现相同值，同步完成后触发一次本地重编号 |

**明确不做 CRDT**（不用 automerge/yrs）：单人多设备场景下，
逐字段 LWW + 集合并集已经够用，引入 CRDT 会让数据结构彻底绑死在第三方库上。

## 5. 同步流程

```
手动/自动触发
   │
   ├─ ① pull：ListObjectsV2(prefix) 拿远端对象清单（只有 key + ETag，很便宜）
   │     与本机「上次同步快照」比对 ⇒ 得出「远端新增/变更/删除」
   │
   ├─ ② 合并：对每个变化的实体
   │     · 本机没改过 → 直接落库
   │     · 两边都改过 → 按 §4 合并
   │     · 远端是墓碑 → 本地也删（软删）
   │
   ├─ ③ push：把本机变化的实体 PutObject
   │     · 首次上传用 If-None-Match: *（防覆盖别人的）
   │     · 覆盖用 If-Match: <已知 ETag>（防覆盖并发写）
   │     · 409/412 ⇒ 回到 ② 重新合并该实体（乐观锁重试）
   │
   └─ ④ 落快照：记录本次同步后的 (id → rev/ETag)，供下次比对
```

**加密**：每个对象自己 AES-GCM 加密；**主密钥**由用户在设置里生成/填写（`§6`），
用 Android Keystore 保护的密钥再包一层后存 `app_meta`。
丢了主密钥 = 云端数据无法解密（会在设置页明确警告，见 §8）。

## 6. 设置页设计（用户要求加的部分）

主设置页「通用」区下方新增一节 **「同步」**：

```
同步
┌──────────────────────────────────────┐
│ ☁ 云同步                    [开关]    │   ← 关闭时下方灰显
├──────────────────────────────────────┤
│ 账号与连接         未配置 >           │   → 「云同步设置」页
│ 上次同步           从未 / 3 分钟前 >  │
│ 立即同步           12 项待上传 >      │

```

**「云同步设置」页**（新路由）分三块：

| 分区 | 内容 |
| --- | --- |
| **连接** | R2 账号 ID、存储桶名、Access Key ID、Secret Access Key、路径前缀。底部「测试连接」按钮（走 `HeadBucket`） |
| **安全** | 主密钥：生成 / 导入 / 显示备份码（一长串，让用户抄走）。⚠️ 红字警告「丢失后云端数据无法恢复」 |

（与目标设置页同源），底部保存走 `VBottomActionBar` + `VPrimaryButton`。

### S6：为什么没用 WorkManager

原计划写的是 WorkManager。实施时改用 **AlarmManager**（与项目既有的提醒功能同一套机制）：

· **语义匹配**：WorkManager 保证的是"最终会执行"，适合"必须完成"的后台任务；
  而自动同步是**尽力而为**的 —— 失败了下一次再试就行，系统为省电延后也完全可以接受。
  为"尽力而为"引入一套"保证执行"的框架（+ 传递依赖）是拿复杂度换不需要的东西。
· **项目已证明这套可行**：`ReminderAlarms` 用的就是 AlarmManager，
  并且已经处理好重启后重建（`BootReceiver`）。

用 `setInexactRepeating`（每 6 小时）：同步不是差一分钟都不行的事，
而不精确闹钟能被系统与其他唤醒**合并**，对续航更友好。

**覆盖安装也要重排**（`ACTION_MY_PACKAGE_REPLACED`）—— 那是本项目最常见的交付方式，
用户更新一次版本，同步闹钟不该就此消失。

### S6：回收功能里最容易写错、也最难发现的一条

**只回收已经上传成功的墓碑**，判据是存在 HLC（它只在一次成功同步之后才被写上）。

删掉没同步出去的墓碑 = 云端不知道要删 ⇒ 那台设备上它**永远不会消失**，
甚至会被当作"新增"传回来。

而且这个问题**不会立刻显形**：表现是几天后某台设备上"删掉的东西又回来了"，
那时已经很难追到是回收干的。所以单独成一个判据，配 3 条测试锁死
（未同步的不删 / 不够老的不删 / 90 天边界取 `>=`）。

90 天是**保守值，不是精确值** —— "所有设备都知道这条被删了"无法精确判定
（一台设备可能半年没开）。缩短会让长期离线设备复活已删数据；拉长只是多占空间。

### S5 的一个真 bug：格式不一致（只有测试能抓到）

原本写成「逐片加密、每片 AAD 带片号」—— 看起来更严谨，但它让
**单次上传与分片上传产出的对象格式不同**：

| 路径 | 对象内容 | 下载侧需要的 AAD |
| --- | --- | --- |
| 单次上传 | 一个完整 GCM 密文 | `objectKey` |
| 分片上传 | N 个独立密文拼接 | `objectKey + 片号` |

而下载侧**并不知道这个对象当初是怎么传的** ⇒ 大附件传上去就再也下不回来。
小文件复现不了（它走单次路径）。

修法：**先整体加密、再切密文**。两条路径产出的对象格式完全一致，
下载侧永远只做 `decrypt(整个对象, aad = objectKey)`。用一点内存换掉一整类 bug。

**顺序上的两个决定**：
· 二进制放在**表同步之后** —— 索引几秒同步完，另一台设备立刻看得见"有这张图"；
  几十 MB 的 PDF 若混在中间传，用户看到的是"同步卡住了"。
· 二进制失败**不改写 error** —— 文字数据已经同步成功，那是有价值的成果。

### S4 的关键决策：流程一份，差异走适配器

引擎在 S3 是给 `items` 写死的。铺开时若复制七份，就会有**八份同步流程** ——
而流程里每条纪律都是踩坑换来的（先合并再上传、本机没有时必须更新、
远端元数据要覆盖本机时钟、墓碑要同步登记处）。复制八份 = 同样八个坑埋八遍。

因此：**`SyncEngine` 一份流程 + `SyncTableAdapter` 承载各表差异**
（`readAll()` / `applyToLocal()` / `payloadKey`）。

**「打包整个闭包」的两处**：
· **白板卡片**连同清单项、标签关联、卡片关联一起走一个对象 ——
  拆开会产生"父级已到、子级还在路上"的中间态。关联只存 id（被引用对象自己也是顶层实体）。
· **课程**连同上课安排一起走，落库时整体替换。

**DI 的一处妥协**：Dagger 的 `@IntoSet` + 构造注入 `Set<T>` 在当前
Dagger KSP 下抛 ClassCastException（工具链问题）。改为 `SyncModule` 的显式
`@Provides` 列表 —— 装配关系一眼看得全，且不引新依赖。

### S3 落地时发现的三个真 bug（记录以免将来重犯）

这三个都是**测试抓出来的**，不是靠读代码看出来的。同步的 bug 只在"两端状态不同"时暴露：

1. **新设备永远同步不下来任何东西**：把"本机要不要更新"写成「合并结果 ≠ 远端」，
   于是 `本机没有 + 远端有` 时合并结果等于远端 ⇒ 判为不用更新 ⇒ 首次下载被静默跳过。
   **只在"一端有数据、另一端首次接入"时暴露** —— 正是用户第一次用的场景。
   正确判据是拿**本机**那份（`localEnvelope == null` 即需要更新）。
2. **远端 HLC 被本机时钟覆盖 ⇒ 永不收敛**：仓储的 `create/update` 会盖本机时钟，
   所以必须**业务行先写、远端元数据后覆盖**（反过来会把远端的时钟冲掉，
   本机看起来"刚改过"，下轮又传回去）。
3. **远端删除后界面仍可见**：收了墓碑但没更新 `TombstoneRegistry` 的内存集合，
   要等下次冷启动才消失。

另外一处**测试自身**的错误值得记：失败注入放在了列表分支之后，导致"凭据错误"
用例假绿。**假绿比红更危险**。

### S2 实际落地与设计的差异（记录以免将来对不上）

· **零第三方依赖**：原计划引 OkHttp，实际未引 —— `HttpURLConnection` 覆盖了全部所需
  （自定义头、流式读写、超时），而 APK 只有 4.5MB，"体积轻便"是用户的验收标准之一。
  AWS SDK 同理未引，SigV4 手写并用**两份独立实现交叉验证**。
· **主密钥的存储保护比原设计弱**：原写"用 Keystore 包裹"，实际是 `app_meta` 里的
  Base64 明文。原因是 Android 上没有"设备锁屏时仍可用"的硬件密钥 ——
  Keystore 密钥锁屏后不可访问，会直接破坏后台同步；而这把密钥本来就必须可导出
  （用户要抄备份码到另一台设备）。真正要做强保护应引用户口令（PBKDF2/Argon2），
  而不是假装 Keystore 能解决。理由已写进 `SyncKeyStore` 的注释。
· **S1 顺带修掉的三处真实缺陷**（见 0.3.29 提交说明）：
  附件索引行被连带删除会导致文件永久丢失；子表读取会漏出已删父级；
  删除子树用"可见集合"找子树会留下没打墓碑的孤儿。

**先做 S1 的理由**：它是唯一的破坏性改动（硬删→软删），
必须**在没有任何网络代码干扰**的情况下先做完并验证「行为与现在一致」。
否则一旦同步出问题，无法判断是软删的锅还是网络/合并的锅。
